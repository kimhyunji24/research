## 1. 우리 연구의 주장별로 가장 가까운 선행연구

| 우리 주장·설계 | 가장 가까운 선행연구 | 겹침 | 우리에게 남는 차별점 |
|---|---|---|---|
| hidden state 프로브로 에이전트 실패를 초반에 예측 | **Doomed from the Start** (Ruan 등, 2607.06503, 초록 확인) | 높음: teacher forcing, 라운드별, 과제 단위 그룹 분할, 3B급 모델 | 그들은 "행동만 보는 모니터보다 낫다"고 보고. **과제 난이도 통제나 과제 내 평가는 초록·10-15 확인 범위에 없음.** 우리는 같은 질문을 난이도 통제 아래 검증해 "텍스트·진행도 baseline보다 낫다는 증거 없음"을 얻음 |
| 높은 pooled AUROC는 과제 난이도 때문일 수 있다, 과제 내 평가가 필요 | **It's the Problem, Not the Path** (Bulut, 2609.03436, 초록 확인) | **매우 높음**: 사전 등록, 난이도 baseline, 문제 내 평가, 재시작 대조까지 있음. pooled 0.849가 문제 내에서는 우연 수준(0.496) | **수학 추론만** 다룸(에이전트·다단계 환경 없음, 모델 2개, 크기 비교 없음). 우리는 **에이전트 환경**에서, 문제 내에서도 step 2~3은 우연보다 높게 나옴(프로브·baseline 모두) |
| 작은 모니터로 조기 중단 | **Fail-Fast, Restart-Smart** (2608.03222, 초록 확인), **AgentStop** (2605.15206, CAIS 2026, 검색 요약), **EarlyEval** (2609.02783, 초록 확인) | 높음: 실용 시스템은 이미 여럿 | 셋 다 hidden state를 쓰지 않음(텍스트·로그확률·행동 특징). 우리는 "hidden state가 이것들보다 나은가"를 직접 비교 |
| 겉보기 신호 vs 내부 신호 비교 | **Monitoring Web Agents Without Internal Signals** (2609.02057, 초록 확인) | 중간: "겉보기 신호가 내부 신호와 경쟁할 만하다" | 웹 에이전트. 내부 신호가 로짓 수준인지 hidden state인지 확인 필요 |
| 같은 과제 반복 시 hidden state는 run 단위 정답을 못 맞힘 | **When Agents Commit Too Soon** (2606.22936, 10-15 확인) | 중간 | HotpotQA·70B. 우리 게임 내 결과와 일관 |
| 작은 reader가 큰 모델 궤적을 읽음(actor/reader 분리) | 직접 해당 연구 **찾지 못함**. 텍스트를 읽는 작은 모니터(CoT-Guard 2605.12746 등)와 "cross-model probe는 향후 과제"라는 언급(2604.13759)만 있음 | 낮음 | **차별점으로 유지 가능**(단, 우리 결과는 크기 효과 없음, 검정력 제한) |
| 질문 단위 목표(P(IK), semantic entropy probe) | Kadavath 2022, Kuhn 2023, Kossen 2024, No Answer Needed (2509.10625, ICLR 2026 워크숍) | 배경 | 과제 단위 목표의 정당성 근거 |
| 실패 기록이 다음 실패를 부름, 기록 지우기 | Illusion of Diminishing Returns (2509.09677, ICLR 2026), AgentRewind (2608.14380), Plans Fade Fast (2606.22953, ALFWorld), DeLoop (2610.19376) | "밧줄" 실험과 높음 | 보류 권장 |

## 1-1. 핵심 3편 본문 정독 (2026-10-17, arXiv HTML 본문 확인)

WebFetch로 본문을 읽어 요약한 것이다. 표·그림 수치는 논문 본문 기준이지만, 인용 전 PDF로 한 번 더 대조한다.

### Doomed from the Start (Ruan 등, 2607.06503 v2, 2026-07, 프리프린트)
| 항목 | 내용 |
|---|---|
| 설정 | TextCraft(100과제 x 8 rollout, 최대 20라운드), WebShop(200과제 x 4, 최대 10라운드). 모델 Llama-3.2-3B, Qwen-2.5-7B, Qwen3-1.7B. 셀당 800 episode. **디코딩 온도 미기재** |
| 프로브 | 라운드 r의 action 마지막 토큰 residual stream, 모델당 layer 1개(층 sweep로 선택). 표준화 + 로지스틱(C=1). **과제 단위 stratified group k-fold 교차적합** |
| baseline | 행동 특징만: action 토큰 평균 로그확률(현재·이전), 생성 토큰 수, prefix 길이, 오류 키워드 수. **과제 문장·관찰 텍스트·진행도·과제 유형은 없음** |
| 주요 수치 | 라운드 1 프로브 AUC: TextCraft Qwen-2.5-7B 0.86, Qwen3-1.7B 0.81. WebShop Qwen3-1.7B 0.591(r1) → 0.896(r3). 행동 baseline의 라운드별 AUC 수치는 본문에 없음(서론에 정성적 서술만) |
| ALFWorld(부록 E) | Qwen-2.5-7B 477 rollout/120과제, 프로브 AUC 0.815(Qwen3-1.7B 0.764) |
| 난이도 통제 | **없음.** 과제 내 평가, 난이도 공변량, "결과가 과제에 의해 정해진다"는 논의 모두 없음. 과제당 4~8 rollout이 있어 과제 내 평가가 가능한 데이터인데도 하지 않음 |
| 크기 | 크기를 변수로 분석하지 않음(모델마다 layer가 달라 통제된 비교 아님) |
| 내부 불일치 | 본문의 Qwen3-1.7B ALFWorld 절감 "11–4%"와 표 4의 2.4–4.3% 불일치 |
| 코드·데이터 공개 | 확인 못 함(검색에서 찾지 못함, 확인 필요) |

**우리에게 의미:** 그들의 "행동만 보는 모니터는 약하다"는 결론은 **과제 정보가 빠진 약한 baseline** 대비다. 우리 사다리에서는 과제 유형(2단)만으로 0.603, 텍스트 포함(5단)으로 step 0에 0.701이 나왔고, 이를 넣으면 프로브 우위가 사라졌다. 이 차이를 직접 보이면(아래 B7) 가장 날카로운 기여가 된다.

### It's the Problem, Not the Path (Bulut, 2609.03436, 2026-09, 단독 저자 프리프린트)
| 항목 | 내용 |
|---|---|
| 설정 | **수학만**(MATH 89문제 x 모델 2 = 178 셀). Gemma-4 E4B, Ministral-3 3B, 4-bit MLX, thinking 모드, T=0.6. 공개 덤프(DeepSeek-R1 192K 생성, R1-Distill-7B 128문제 x 256 샘플, GPQA) 재분석 |
| 난이도 baseline(사전 등록) | 인간 난이도 등급, 주제, 문제 텍스트 표면 통계 5개, 모델 식별자 |
| 사전 등록 결과 | 주 지표 baseline 0.83 vs 초반 신호 추가 0.85, Δ = +0.026 [−0.054, +0.167] → 이득 검출 안 됨. 동등성 마진은 사전 등록 안 함 |
| 문제 내 평가 | 쌍 AUROC(동점 ½), 실패 수 가중(사전 등록) 0.496 [0.466, 0.527], 쌍 가중 0.515 [0.481, 0.562]. 문제 단위 percentile bootstrap(2,000회) |
| 재시작 대조 | 같은 토큰 예산에서 prefix 이어 쓰기 vs 처음부터: 9/9에서 이어 쓰기가 이김. prefix가 꼭 필요한 셀은 178개 중 1개 |
| 한계(스스로) | 모델 2개, 수학만, 확증 baseline이 텍스트 수준이고 **활성 프로브와의 비교는 아님**, 셀당 시도 4~8 |
| 다루지 않음 | 에이전트·다단계 환경, **동일 prefix(동점 쌍) 문제**, bootstrap CI 포함률 점검 |

**우리에게 의미:** 아이디어(난이도 교락, 문제 내 평가)는 선행. 그러나 (1) 에이전트 환경, (2) 활성 프로브 vs 텍스트·진행도 사다리의 직접 비교, (3) **이산 action 에이전트에서 rollout이 초반에 같은 prefix를 공유해 생기는 동점 희석**(우리 52~70%), (4) **문제 단위 percentile bootstrap CI가 명목보다 좁다는 null 보정 결과**(우리 80~94%, Bulut도 같은 종류의 CI를 씀)는 우리 고유의 방법론적 기여가 된다. 다만 (4)는 우리 데이터 39게임 기준이라 일반화는 확인 필요.

### Fail-Fast, Restart-Smart (Wang 등, 2608.03222 v1, 2026-08, 프리프린트)
| 항목 | 내용 |
|---|---|
| 모니터 | Qwen3-0.6B + LoRA, 입력은 [ISSUE] + 최근 8 step 텍스트. 최종 결과 + 중간 F2P/P2P 진행도 라벨 |
| 데이터 | SWE-bench Verified 500 인스턴스 x 11 run(Qwen3.6-27B), 인스턴스 단위 분할 350/50/100 |
| baseline | AgentStop(로그확률·토큰 수·반복, GBDT): 5% FPR에서 12.5% 절감 vs FailFast 20.4%. **step 수만 쓰는 대조: 11.4%**. hidden state·로그확률 프로브는 관련 연구로만 언급 |
| 난이도 | 과제 내 평가 없음. [ISSUE] 입력을 빼면 recall이 떨어짐(표 5) → 모니터가 과제 정보를 상당히 쓴다는 정황 |
| 재시작 | 25% FPR: 66.6% → 71.8%(+5.2), cold restart +0.2. 재시작 비용 +43.8% 토큰 |
| 비용 단위 | 실행 토큰 절감 %. **모니터 비용은 policy의 0.1~0.6%로 추정**(27B policy 대비) |
| hidden state를 안 쓴 이유 | 닫힌 API 모델도 감시하기 위해(white-box 불필요) |

**우리에게 의미:** (1) step 수만으로 11.4%를 아낀다는 대조가 이미 강하다 → 우리 조기 중단 비교에도 cap/step 규칙을 반드시 넣는다(계획에 있음). (2) **모니터 비용이 무시 가능한 것은 policy가 27B이기 때문**이다. 우리 3B actor에서는 0.5B 약 13%, 7B 약 180%라 무시할 수 없다. 소형 actor 환경에서는 "모니터 포함 계산량"이 맞는 비용 단위라는 근거가 된다(비용 단위 결정에 사용).

### 결론: 새롭다고 말할 수 있는 범위가 좁아졌다
- "난이도 교락 때문에 과제 내 평가가 필요하다"는 아이디어 자체는 **Bulut(2026-09)이 수학 추론에서 먼저** 했다. 우리 연구가 그보다 먼저 설계됐더라도(2026-10-15 사전 기록), 논문에서는 반드시 인용하고 비교해야 한다.
- 남는 기여(확인 범위 내):
  1. **에이전트(다단계 상호작용) 환경**에서 hidden state 실패 예측을 난이도 통제와 과제 내 평가로 검증한 것. Doomed from the Start 같은 에이전트 프로브 주장을 엄격하게 재검토한다.
  2. hidden state와 **텍스트·진행도 baseline 사다리**를 같은 분할·같은 통계로 비교한 사전 등록 부정 결과.
  3. **actor/reader 분리**로 표현 크기(0.5B~7B)만 바꾼 비교.
  4. 문제 내에서도 신호가 0은 아니라는 결과(step 2~3). 단 프로브만의 우위는 없다. Bulut의 "문제 내 우연 수준"과 다른 점이라 토의 거리가 된다.

## 3. 추천 순서 (제안, 결정 필요, 본문 정독 후 갱신)
1. A1~A3 완료(진행 중)
2. **B7**(Doomed식 baseline 재현) + B1, B2 → 선행연구와의 관계를 한 표로 보여 줌. CPU, 짧음
3. B5(프로브 강화) → 부정 결과 방어. 그다음 B3, B4
4. C1 사전 등록: 비용 단위는 "모니터 포함 계산량" 주, step 보조로 제안(근거: Fail-Fast의 모니터 비용 0.1~0.6%는 27B policy 기준이고 소형 actor에서는 성립하지 않음)
5. D1: Doomed의 코드·데이터가 공개돼 있으면 **그들의 TextCraft rollout(과제당 8회)을 재분석**하는 것이 GPU 없이 가장 싼 일반화 방법이다(공개 여부 확인 필요). 없으면 TextCraft 소규모 수집을 검토
6. 서론의 기여 서술을 "에이전트 환경에서 난이도 통제 아래 hidden state 모니터를 재검토"로 고정하고 Bulut을 선행 아이디어로 명시

## 4. 사용자 결정 (2026-10-17, 문서·저장소 반영 전)
- 연구 질문: "에이전트 hidden state 실패 신호는 과제 난이도를 읽는가 진행 중 실패를 읽는가, 그 답은 모델 크기·계열에 따라 어떻게 바뀌는가"
- 환경은 ALFWorld 하나로 고정. 새 환경(TextCraft 등)과 "밧줄 풀어 주기" 실험은 하지 않음
- 1.5B 이하는 크기로 빼지 않고 사전 포함 기준으로 거름(파일럿 20 episode 중 3개 이상 성공, 기준은 파일럿 전에 사전 기록)
- **모델 확장은 최소안(선택지 2)**: Llama-3.2-3B(같은 크기·다른 계열), Qwen3-4B(더 큼·최신). 모델당 본 수집 250 episode + 다중 rollout 50게임 x 8회, GPU 합계 약 5~6시간(추정, 확인 필요). 모델별로 따로 보고하고 기존 결과와 합치지 않음
- 미정: 파일럿에 다른 후보(Qwen3 0.6B/1.7B/8B 4-bit 등)를 함께 넣을지, 시간 한도 100을 새 모델에도 할지
